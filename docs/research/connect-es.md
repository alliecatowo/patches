## 1. buf.gen.yaml plugin config for `protoc-gen-es` v2

Two working forms, both seen in official sources:

```yaml
# connectrpc.com/docs/node/getting-started (doc form, opt as scalar)
version: v2
plugins:
  - local: protoc-gen-es
    out: gen
    include_imports: true
    opt: target=ts
```

```yaml
# github.com/connectrpc/examples-es, vanilla-node/buf.gen.yaml (real repo, opt as list)
version: v2
clean: true
inputs:
  - module: buf.build/connectrpc/eliza
plugins:
  - local: protoc-gen-es
    out: gen
    opt:
      - target=ts
```

Both `opt: target=ts` (scalar) and `opt: [target=ts]` (list) are valid buf.gen.yaml v2 syntax; the repo's
own `nestjs-grpc-protobuf.md` note already documents scalar `opt:` for ts-proto, so either form is fine —
pick one project-wide for consistency. `local: protoc-gen-es` resolves the binary from
`node_modules/.bin/protoc-gen-es` (same mechanism as the existing `local:` ts-proto plugin block); I did
not find a `remote:` form documented for protoc-gen-es specifically, only `local:`, in the getting-started
doc or the examples repo.
Source: connectrpc.com/docs/node/getting-started (fetched); github.com/connectrpc/examples-es/blob/main/vanilla-node/buf.gen.yaml

**Output naming and file contents** — confirmed by reading a real generated file
(`github.com/connectrpc/examples-es/blob/main/vanilla-node/gen/connectrpc/eliza/v1/eliza_pb.ts`,
generated by `protoc-gen-es v2.6.2 with parameter "target=ts"`):

- One `<proto-file-stem>_pb.ts` per `.proto` file (e.g. `eliza.proto` → `eliza_pb.ts`; for this repo,
  `system.proto` → `system_pb.ts`).
- **A single file contains both message classes/types AND service descriptors** — there is no separate
  services file. This differs from some other codegen tools (e.g. `protoc-gen-connect-es`, which
  Connect-ES v2 dropped per ADR 0016's own research) that used to split them.
- Every file exports a `GenFile` const named `file_<package_path_with_underscores>` (e.g.
  `file_connectrpc_eliza_v1_eliza`), built via `fileDesc(base64Bytes)` from `@bufbuild/protobuf/codegenv2`
  — the whole `FileDescriptorProto` is embedded as a base64-encoded blob, not re-derived from JS.
- Each message gets a `{MessageName}Schema` const (`GenMessage<...>`, e.g. `SayRequestSchema`) built via
  `messageDesc(file_..., index)`.
- **Each service gets a const named exactly the service name** (e.g. for `service ElizaService` →
  `export const ElizaService: GenService<{...}> = serviceDesc(file_..., index)`). For `service
SystemService` in `patches.v1`/`system.proto`, the emitted symbol would be
  `export const SystemService: GenService<{...}>`.
- `GenService<T>`'s type parameter is a record of method-name → `{ methodKind, input, output }`, one key
  per RPC, keyed by the method's `localName` (camelCase).

## 2. Enumerating services/methods at runtime

Confirmed by reading `packages/protobuf/src/descriptors.ts` and `packages/protobuf/src/codegenv2/{types,service,file}.ts`
in github.com/bufbuild/protobuf-es (main):

- `GenFile` **is** `DescFile` (`export type GenFile = DescFile;` — codegenv2/types.ts), and `DescFile` has
  a real, populated `readonly services: DescService[]` field (descriptors.ts line 134). `serviceDesc()`
  itself is implemented as `return file.services[path] as GenService<T>;` — i.e. the generated
  `{ServiceName}` const is literally `file_xxx.services[N]`, so **`file_xxx.services` is a genuine,
  walkable array at runtime**, not merely a type-level convenience. This is the correct way to enumerate
  every service in one `_pb.ts` file generically: import the `file_...` const from each generated module
  and iterate `.services`.
- protoc-gen-es v2 does **not** emit a barrel file listing every generated file/service — there's no
  index re-exporting them. For a generic proxy across many `.proto` files, the calling code must either
  (a) import each `file_...` const explicitly (one import per proto file — 13 for this repo's 13
  services, assuming roughly one service per file) and concatenate `.services`, or (b) maintain the
  list of generated files as a small manually-written array in `packages/proto`. I found no documented
  buf/protoc-gen-es mechanism to auto-discover generated files at runtime — inferred: this list must be
  hand-maintained or built at codegen time, which matches ADR 0016's plan to keep `@patches/proto/es` as
  a package that can export such a list itself.
- `DescService.methods: DescMethod[]` (array) and `DescService.method: Record<string, DescMethod>`
  (keyed by `localName`) both exist (descriptors.ts lines 665–697).
- `DescMethod` (descriptors.ts lines 702–743) confirmed fields: `kind: "rpc"`, `name`, `localName` (camelCase
  JS method name), `parent: DescService`, `methodKind: "unary" | "server_streaming" | "client_streaming" |
"bidi_streaming"`, `input: DescMessage`, `output: DescMessage`, `idempotency`, `deprecated`, `proto`. So
  `methodKind === 'unary'` is the correct/only check needed for ADR 0016's "fail if a .proto ever
  introduces streaming" guard, and `input`/`output` are `DescMessage`s directly usable with
  `toBinary`/`fromBinary` (§3).

Source: github.com/bufbuild/protobuf-es/blob/main/packages/protobuf/src/descriptors.ts;
github.com/bufbuild/protobuf-es/blob/main/packages/protobuf/src/codegenv2/{types.ts,service.ts,file.ts}

## 3. `toBinary`/`fromBinary`

Confirmed by reading `packages/protobuf/src/{to-binary,from-binary,index}.ts` in bufbuild/protobuf-es:

- Both are exported from the **package root** `@bufbuild/protobuf` (`index.ts`: `export { toBinary } from
"./to-binary.js";` and `export { fromBinary, mergeFromBinary } from "./from-binary.js";`) — no subpath
  needed for these two functions (subpaths like `@bufbuild/protobuf/codegenv2` and
  `@bufbuild/protobuf/wkt/...` exist for other things, e.g. what generated `_pb.ts` files import, but not
  for `toBinary`/`fromBinary`).
- Exact signatures (from source):
  ```ts
  function toBinary<Desc extends DescMessage>(
    schema: Desc,
    message: MessageShape<Desc>,
    options?: Partial<BinaryWriteOptions>,
  ): Uint8Array<ArrayBuffer>;

  function fromBinary<Desc extends DescMessage>(
    schema: Desc,
    bytes: Uint8Array,
    options?: Partial<BinaryReadOptions>,
  ): MessageShape<Desc>;
  ```
  This confirms the question's assumed signature (`toBinary(messageDesc, messageValue): Uint8Array`,
  `fromBinary(messageDesc, bytes): MessageShape`), modulo the optional third `options` arg.

Source: github.com/bufbuild/protobuf-es/blob/main/packages/protobuf/src/to-binary.ts;
github.com/bufbuild/protobuf-es/blob/main/packages/protobuf/src/from-binary.ts;
github.com/bufbuild/protobuf-es/blob/main/packages/protobuf/src/index.ts

## 4. `expressConnectMiddleware` and request body handling

Confirmed by reading `packages/connect-express/src/express-connect-middleware.ts` in connect-es (main):

- Import: `import { expressConnectMiddleware } from "@connectrpc/connect-express";`
- Signature: `expressConnectMiddleware(options: ExpressConnectMiddlewareOptions): express.Handler`, where
  `ExpressConnectMiddlewareOptions extends ConnectRouterOptions` and adds `routes: (router: ConnectRouter)
=> void`, `requestPathPrefix?: string`, `contextValues?: (req) => ContextValues`. It **returns a plain
  Express `RequestHandler`** meant for `app.use(expressConnectMiddleware({ routes }))` — confirmed in the
  official example server (`connectrpc/examples-es/express/server.ts`).
- **Body handling — this is the load-bearing finding.** The middleware does not blindly require an
  untouched stream. Its handler calls
  `universalRequestFromNodeRequest(req, res, getPreparsedBody(req), options.contextValues?.(req))`, where
  `getPreparsedBody(req)` is a small helper whose doc-comment says verbatim:
  > "This supports the very popular npm package 'body-parser', which reads the body of an incoming
  > request, parses it as JSON if the Content-Type header **ends** with 'json', and stores it on the
  > request object in the 'body' property. The recommended way to use body-parser is to add it to
  > specific routes instead of globally, but we have no control over this."
  > It returns `undefined` if `req.body` is `null`/`undefined` (i.e. not pre-parsed).
- In `connect-node`'s `universalRequestFromNodeRequest` (the function connect-express calls), the body is
  resolved as: `parsedJsonBody !== undefined ? parsedJsonBody : asyncIterableFromNodeServerRequest(nodeRequest)`
  — i.e. **if no pre-parsed `req.body` is present, it reads the raw Node request stream itself.** So:
  - A route-scoped or global **JSON** body-parser (Express's `express.json()`/`body-parser`) is
    _tolerated_ — it only intercepts requests whose `Content-Type` ends with `json`, which lines up with
    Connect's JSON codec, and connect-express will use the already-parsed `req.body` in that case instead
    of re-reading the stream.
  - For **binary** Connect requests (`Content-Type: application/proto`, which is what ADR 0016's
    byte-passthrough plan implies), a JSON-only body-parser does not match the content-type and will not
    consume the stream (this is `body-parser`'s own content-type-matching behavior — not something I
    verified inside connect-es itself, so treat this specific claim as **inferred**, not
    connect-es-documented) — connect-express then reads the raw stream itself.
  - I found **no explicit official-doc warning** telling you not to run a JSON body-parser upstream —
    only the source-code fallback behavior above, plus the fact that the official Express example
    (`server.ts`) does **not** call `express.json()`/`app.use(express.json())` at all before
    `expressConnectMiddleware`. Given Nest's Express adapter installs `bodyParser.json()` and
    `bodyParser.urlencoded()` globally by default, **verify this interaction with an integration test**
    before relying on it (flagged for the implementer, not asserted as safe here).

Source: github.com/connectrpc/connect-es/blob/main/packages/connect-express/src/express-connect-middleware.ts;
github.com/connectrpc/connect-es/blob/main/packages/connect-node/src/node-universal-handler.ts;
github.com/connectrpc/examples-es/blob/main/express/server.ts

## 5. `ConnectRouter.service(serviceType, implementation)` — decoded, not raw bytes

Confirmed by reading `packages/connect/src/router.ts` and `packages/connect/src/implementation.ts` in
connect-es (main):

```ts
service: <T extends DescService>(
  service: T,
  implementation: Partial<ServiceImpl<T>>,
  options?: Partial<UniversalHandlerOptions>,
) => this;

type ServiceImpl<Desc extends DescService> = {
  [P in keyof Desc['method']]: MethodImpl<Desc['method'][P]>;
};

type UnaryImpl<I extends DescMessage, O extends DescMessage> = (
  request: MessageShape<I>,
  context: HandlerContext,
) => Promise<MessageInitShape<O>> | MessageInitShape<O>;
```

**This settles the question definitively: `ConnectRouter.service`/`.rpc` hand your implementation an
already-decoded protobuf-es message instance (`MessageShape<I>`) and expect a decoded response
(`MessageInitShape<O>`) back — there is no raw-bytes hook at this layer.** The router decodes the
Connect-envelope-wrapped request body (JSON or binary, whichever the client sent) into a full message
using `I`'s descriptor before your handler runs, and re-encodes whatever your handler returns using `O`'s
descriptor. This confirms ADR 0016 §3's stated design is correct and necessary: the "byte-level proxy" is
byte-level only with respect to grpc-js (decode once at the Connect edge → `toBinary` → send raw bytes to
grpc-js over loopback → `fromBinary` the grpc-js response → return it), not a true zero-decode passthrough
end-to-end. There is no lower-level API in `@connectrpc/connect` that skips this decode/encode step for a
registered handler.

Source: github.com/connectrpc/connect-es/blob/main/packages/connect/src/router.ts;
github.com/connectrpc/connect-es/blob/main/packages/connect/src/implementation.ts

## 6. CORS

**Real, verified export** — `cors` is exported from `@connectrpc/connect` itself (not connect-node or
connect-express), confirmed both by the official Express example and by grep of the doc summary
referencing `/docs/node/server-plugins/#cors`:

```ts
import { cors as connectCors } from '@connectrpc/connect';
import cors from 'cors'; // npm 'cors' package

const corsOptions: cors.CorsOptions = {
  origin: true, // dev only; specify explicit origins in prod
  methods: [...connectCors.allowedMethods],
  allowedHeaders: [...connectCors.allowedHeaders],
  exposedHeaders: [...connectCors.exposedHeaders],
};
app.use(cors(corsOptions));
```

This is copied verbatim (modulo comments) from `github.com/connectrpc/examples-es/blob/main/express/server.ts`,
which is a maintained official example, not a blog post. So `connectCors.allowedMethods`,
`.allowedHeaders`, `.exposedHeaders` are real arrays meant to be spread into the npm `cors` package's
config — ADR 0016 §6 ("`cors` from `@connectrpc/connect` for allowed/exposed headers") is directly
supported by this. I did not separately fetch a `connectrpc.com/docs/node/cors` page with full prose (the
doc summary only confirmed a `#cors` anchor on `/docs/node/server-plugins`); the example code above is the
higher-confidence source.

Source: github.com/connectrpc/examples-es/blob/main/express/server.ts (official example);
connectrpc.com/docs/node/server-plugins#cors (referenced but not fully read)

## 7. gRPC status codes vs Connect `Code` — numerically identical

Confirmed by reading the raw source of both enums directly:

- `@connectrpc/connect`'s `Code` enum (`packages/connect/src/code.ts`): `Canceled = 1, Unknown = 2,
InvalidArgument = 3, DeadlineExceeded = 4, NotFound = 5, AlreadyExists = 6, PermissionDenied = 7,
ResourceExhausted = 8, FailedPrecondition = 9, Aborted = 10, OutOfRange = 11, Unimplemented = 12,
Internal = 13, Unavailable = 14, DataLoss = 15, Unauthenticated = 16`. The file's own doc-comment states:
  "The codes and their semantics were chosen to match gRPC. Only the codes below are valid — there are no
  user-defined codes."
- `@grpc/grpc-js@1.14.4`'s `Status` enum, read directly from this repo's installed copy
  (`node_modules/.pnpm/@grpc+grpc-js@1.14.4/.../build/src/constants.js`): `OK = 0, CANCELLED = 1, UNKNOWN =
2, INVALID_ARGUMENT = 3, DEADLINE_EXCEEDED = 4, NOT_FOUND = 5, ALREADY_EXISTS = 6, PERMISSION_DENIED = 7,
RESOURCE_EXHAUSTED = 8, FAILED_PRECONDITION = 9, ABORTED = 10, OUT_OF_RANGE = 11, UNIMPLEMENTED = 12,
INTERNAL = 13, UNAVAILABLE = 14, DATA_LOSS = 15, UNAUTHENTICATED = 16`.
- **These are numerically identical for values 1–16** (Connect has no `0`/`OK` value since `Code` is only
  used for errors — a successful Connect call has no code at all). A direct cast
  `code: grpcStatus as unknown as Code` is numerically valid for any non-zero grpc-js `Status`; no lookup
  table is required. (Still worth a named mapping function purely for type-safety/readability and to
  handle the `OK`/`0` case explicitly — `0` is not a valid `Code` — but the numbers themselves need no
  translation.)

Source: github.com/connectrpc/connect-es/blob/main/packages/connect/src/code.ts (raw source read directly);

## 8. `createConnectTransport` (connect-node) + `createClient`

Confirmed by reading the official example client (`connectrpc/examples-es/vanilla-node/client.ts`) and the
`CallOptions` interface source:

```ts
import { createClient } from '@connectrpc/connect';
import { createConnectTransport } from '@connectrpc/connect-node';
import { ElizaService } from './gen/.../eliza_pb.js';

const transport = createConnectTransport({
  httpVersion: '1.1', // or '2'
  baseUrl: 'http://localhost:3000',
  interceptors: [/* ... */], // applied to every call on this transport
});
const client = createClient(ElizaService, transport);
```

- `createConnectTransport` is exported by `@connectrpc/connect-node` (not `connect-web`, which is the
  browser build using `fetch` directly); `createClient(ServiceType, transport)` is exported by
  `@connectrpc/connect` — confirmed identical import split in both the doc summary and the real example.
- **Per-transport headers**: via an `Interceptor` passed in `interceptors: [...]` at transport-creation
  time, which mutates `req.header` (a `Headers` object) before calling `next(req)`.
- **Per-call headers**: confirmed via source of `CallOptions` (`packages/connect/src/call-options.ts`):
  `headers?: HeadersInit` is a field directly on the per-call options object, which every generated client
  method accepts as its second argument, e.g. `client.say(request, { headers: { Authorization: "Bearer
bad-token" } })`. Same object also carries `timeoutMs`, `signal`, `onHeader`, `onTrailer`,
  `contextValues` — useful for a test that needs to inspect response headers/trailers directly.

Source: github.com/connectrpc/examples-es/blob/main/vanilla-node/client.ts (official example);
github.com/connectrpc/connect-es/blob/main/packages/connect/src/call-options.ts (source, read directly);
connectrpc.com/docs/node (doc summary, httpVersion '1.1'/'2' confirmed)

### 8a. Aborting `CallOptions.signal` surfaces as `Code.Canceled` (B-164)

Confirmed by reading the installed package directly (`@connectrpc/connect@2.1.2`,
`dist/cjs/connect-error.js`): `ConnectError.from(reason)` special-cases a `DOMException`/
error whose `name` is `"AbortError"` or `"TimeoutError"` (the shape `fetch` and
`AbortSignal.timeout()` throw) and converts it to `new ConnectError(reason.message,
Code.Canceled)` — not `Code.Unknown`. So a mutation that passes its own `AbortController`'s
`signal` via `CallOptions.signal` and then calls `.abort()` gets back a `ConnectError` with
`code === Code.Canceled` from the call promise's rejection, on both `connect-web` and
`connect-node` transports (the translation lives in the transport-agnostic `connect-error.js`,
not either transport package). `describeError` (`packages/client/src/errors.ts`) already has a
`Code.Canceled` branch ("Request cancelled.") — a caller that wants to _swallow_ an
intentional unmount-triggered abort (rather than show that copy) needs to check the code
itself before calling `describeError`, e.g. `apps/web/src/hooks/useAbortableMutation.ts`,
which instead skips the callback entirely once its owning component has unmounted.

Source: `node_modules/.pnpm/@connectrpc+connect@2.1.2_@bufbuild+protobuf@2.14.0/node_modules/@connectrpc/connect/dist/cjs/connect-error.js` (installed package, read directly)

## 9. Error propagation — `ConnectError` metadata

Confirmed by reading `packages/connect/src/connect-error.ts` in connect-es (main):

```ts
constructor(
  message: string,
  code: Code = Code.Unknown,
  metadata?: HeadersInit,
  outgoingDetails?: OutgoingDetail[],
  cause?: unknown,
)
```

- Server side: `throw new ConnectError("not authorized", Code.PermissionDenied, { "x-patches-error-code":
"SOME_CODE", "x-request-id": requestId })` — the third constructor arg is a `HeadersInit`, stored as
  `this.metadata = new Headers(metadata ?? {})`. The class comment confirms: `"A union of response headers
and trailers associated with this error."` — i.e. connect-es itself unions the wire's headers/trailers
  into one `Headers` object regardless of transport (HTTP/1.1 vs HTTP/2, Connect vs gRPC-Web protocol),
  so the server doesn't need to reason about the header/trailer distinction.
- Client side (from doc summary of connectrpc.com/docs/web/errors, not independently re-verified against
  source in this pass): catch the error, `if (err instanceof ConnectError) { err.metadata.get("x-patches-error-code")
}`. `findDetails()` is a **different** mechanism — it decodes typed `google.protobuf.Any`-wrapped
  protobuf messages attached as structured error details, not arbitrary string headers; use `.metadata`
  for the two custom headers described in the question, not `.findDetails()`.
- I did not independently trace connect-express's error path to confirm it forwards `ConnectError.metadata`
  as real outgoing HTTP response headers/trailers end-to-end (only read the client-side `ConnectError`
  source and the general docs description) — **recommend an integration test** (server throws with two
  custom metadata entries, connect-node test client asserts both come back on the caught
  `ConnectError.metadata`) as the actual verification, per ADR 0016 Phase A's acceptance criteria.

Source: github.com/connectrpc/connect-es/blob/main/packages/connect/src/connect-error.ts (raw source, read
directly); connectrpc.com/docs/web/errors (doc summary, client-side `.metadata`/`.findDetails()` usage —
not independently re-verified against source)

## Discrepancies with ADR 0016 / things to flag

- ADR 0016 §3 describes the proxy as "byte-level" and implies grpc-js bytes reach it "untouched" — true
  for the grpc-js hop, but **not** true for the Connect-router hop: `ConnectRouter.service`/`.rpc` always
  decode into a full message object before your handler runs (§5 above). This isn't a contradiction of the
  ADR's actual text (which does say "protobuf-es decodes the Connect request... and re-encodes it to
  protobuf binary" — i.e. it already accounts for one decode/encode pair), just a confirmation worth
  keeping explicit so a future implementer doesn't go looking for a raw-bytes registration API that
  doesn't exist.
- No discrepancy found between protoc-gen-es v2's actual generated shape and what ADR 0016 assumed
  (one file per proto with both messages and service descriptors, `GenService`-typed const per service) —
  the ADR's own research note already had this right.
